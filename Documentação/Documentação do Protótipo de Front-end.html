Documentação do Protótipo de Front-end

Projeto: EscolaAlerta

Dupla: Mateus Farias Bentes e Mariana Idalina Bezerra Vidinho

1. Introdução

Este documento descreve a implementação do front-end do protótipo EscolaAlerta: arquitetura de telas, motor de classificação de risco, modelo de dados, sistema de design e catálogo de componentes React. O protótipo cobre dois perfis de uso com jornadas independentes a partir de uma mesma base de dados em memória — orientador escolar e responsável — e existe em duas versões-fonte mantidas em paralelo, descritas na seção 2.

PerfilO que fazTelas
Orientador escolar Cadastra alunos e registra indicadores (nota, falta, ocorrência, saída antecipada). Cada registro recalcula o risco do aluno em tempo real. dashboard → cadastro / registro de indicador
Responsável Acompanha o nível de risco do dependente, lê o plano de ação sugerido pela escola quando há risco e devolve feedback sobre a resolução. painel de risco → plano de ação

Observação: a tela de login é decorativa — os dois botões apenas escolhem qual perfil simular. Não há autenticação real (ver seção 10).

2. Stack e Arquivos

O protótipo existe em duas versões paralelas do mesmo front-end, mantidas manualmente em sincronia: mesma árvore de componentes, mesmo motor de regras, mesmos tokens visuais.

2.1 escolaalerta-prototipo.html

Arquivo único e autocontido: React 18, ReactDOM e Babel Standalone carregados via CDN (cdnjs), com o componente App escrito dentro de uma tag <script type="text/babel"> e transpilado no próprio navegador. Ícones via Font Awesome 6. Não requer instalação nem servidor — basta abrir o arquivo.

2.2 escolaalerta-prototipo.jsx

Mesma aplicação como módulo ES (import/export default), pensada para entrar em um projeto Vite, Create React App ou Next.js já existente. Ícones via lucide-react em vez de classes de fonte. Os tokens de estilo vivem em um componente <GlobalStyle> que injeta a mesma folha de estilos do arquivo .html.

2.3 Por que dois arquivos

O .html serve como demonstração imediata (apresentação, avaliação, revisão de design) sem qualquer configuração. O .jsx é o ponto de partida caso o protótipo evolua para integrar com a API Node.js e o banco PostgreSQL descritos em "Arquitetura da Solução e Padrões de Projeto". Eles não compartilham uma fonte única — alterações precisam ser replicadas manualmente nos dois arquivos (ver seção 10).

4. Motor de Classificação de Risco

A função classificarRisco(aluno) roda no cliente a cada renderização e a cada novo indicador registrado — não há chamada de API. Ela avalia três critérios de forma independente, atribui um peso a cada um e usa o maior peso para decidir o nível final e a causa principal.

CritérioCondiçãoPeso
Ocorrências3 ou mais registradas3
1 ou 2 registradas1
Faltas5 ou mais3
3 ou 42
1 ou 21
Notas abaixo de 62 ou mais disciplinas3
exatamente 1 disciplina1

O nível final é derivado do maior peso entre os critérios que dispararam, e a causa principal é o critério que gerou esse peso (em empate, prevalece a ordem de avaliação: ocorrências → faltas → notas):

Peso máximoNível resultanteEfeito
≥ 3Risco altoPlano de ação acionado
= 2Risco moderadoPlano de ação acionado
≤ 1 ou 0Risco baixoSem plano de ação

4.1 Implementação

function classificarRisco(aluno) { // cada critério é avaliado de forma independente if (nOcorrencias >= 3) causas.push({ tipo: "ocorrencias", peso: 3 }); else if (nOcorrencias >= 1) causas.push({ tipo: "ocorrencias", peso: 1 }); if (nFaltas >= 5) causas.push({ tipo: "faltas", peso: 3 }); else if (nFaltas >= 3) causas.push({ tipo: "faltas", peso: 2 }); else if (nFaltas >= 1) causas.push({ tipo: "faltas", peso: 1 }); if (nNotasBaixas >= 2) causas.push({ tipo: "notas", peso: 3 }); else if (nNotasBaixas === 1) causas.push({ tipo: "notas", peso: 1 }); // vence o critério de maior peso const maxPeso = Math.max(...causas.map(c => c.peso)); const nivel = maxPeso >= 3 ? "alto" : maxPeso === 2 ? "moderado" : "baixo"; }

4.2 Efeito no plano de ação

Somente no momento de um novo registro (dentro do handler onRegistrar do componente App), se o nível recalculado deixa de ser "baixo", a aplicação grava aluno.planoAcao com a causa principal e as sugestões correspondentes, lidas de um dicionário estático SUGESTOES. Alunos já cadastrados em risco na carga inicial dos dados (mock) só recebem plano de ação após o próximo indicador ser registrado — o recálculo não é retroativo aos dados semeados.

5. Modelo de Dados

Todo o estado vive em useState no componente App — não há Context, Redux ou qualquer store externa. Um único array alunos é a fonte de verdade; atualizações passam por atualizarAluno(id, updater), que mapeia o array trocando apenas o aluno afetado.

aluno = { id, nome, turma, responsavel, notas: [{ id, disciplina, valor, periodo }], faltas: [{ id, data, justificada }], ocorrencias: [{ id, descricao, gravidade }], saidas: [{ id, data, horario, motivo }], planoAcao: { causa, sugestoes: [...], nivel } | null, feedbacks: [{ id, status, observacao, data }], }

Três alunos vêm pré-carregados por dadosIniciais() para demonstração: Rafael Costa Lima (já com 3 faltas e 1 ocorrência leve, portanto risco alto por faltas), Ana Beatriz Souza (sem indicadores negativos) e Diego Matos Pereira (uma falta justificada).

6. Sistema de Design

Paleta escura de superfícies neutras com um único acento de cor para ação (azul) e três cores semânticas reservadas exclusivamente para nível de risco — a cor nunca é usada como decoração, apenas para carregar significado. As três cores de risco foram calibradas para contraste mínimo de 4,5:1 (WCAG AA), validado par a par sobre seus fundos reais.

6.3 Elevação e forma

Cartões usam sombra suave em duas camadas — nunca deslocamento duro — e cantos moderados: 12 px em cartões e linhas de lista, 8 px em botões, campos e abas, 6 px em badges. Nenhum elemento usa raio total (border-radius: 999px), decisão deliberada para não competir com os chips de risco.

7. Catálogo de Componentes

Todos os componentes são funções sem estado externo além do useState local — sem hooks customizados, sem memoização, sem Context. A comunicação entre telas é feita exclusivamente por callbacks recebidos via props a partir do componente App.

8. Acessibilidade

Itens verificados manualmente com cálculo de contraste WCAG por par cor-sobre-cor, não apenas por inspeção visual.

  • Rótulos de formulário: todo <label> tem htmlFor ligado a um id real no controle — nenhum campo depende apenas de placeholder.
  • Envio por teclado: todos os formulários de registro são <form> reais com onSubmit; a tecla Enter em qualquer campo envia o formulário.
  • Estado desabilitado explicado: quando o botão de salvar está desabilitado, um texto abaixo dele informa exatamente o que falta preencher.
  • Landmarks semânticos: <header> fixo, <main id="main-content"> por tela, listas reais (<ul>/<li>) para alunos e histórico.
  • Skip-link: link "Pular para o conteúdo", oculto até receber foco por teclado.
  • Notificações: o toast usa role="status" e aria-live="polite" — é anunciado sem roubar o foco do usuário.
  • Contraste de cor: texto secundário ≥ 6,2:1, badges de risco ≥ 4,9:1, texto do botão primário 5,1:1 — todos medidos sobre seus fundos reais.
  • Movimento reduzido: a entrada animada do toast respeita prefers-reduced-motion.
  • Autopreenchimento: campo de e-mail com type="email"; senha com autoComplete="current-password" para gerenciadores de senha.

9. Como Executar

9.1 Versão .html

Nenhuma instalação necessária. Duas opções:

# opção 1 — abrir direto open escolaalerta-prototipo.html # opção 2 — servidor estático local # (recomendado para evitar restrições de file:// em alguns navegadores) python3 -m http.server 8000 # depois abrir http://localhost:8000/escolaalerta-prototipo.html

9.2 Versão .jsx

Requer um projeto React já configurado (Vite, Create React App ou Next.js) com a dependência lucide-react instalada:

npm install lucide-react // main.jsx import App from "./escolaalerta-prototipo.jsx"; // renderizar <App /> na raiz do projeto

10. Limitações Conhecidas

Registradas deliberadamente para deixar claro o que este protótipo demonstra e o que fica para a integração com o back-end descrito nos demais documentos do trabalho.

  • Sem persistência: todo estado é useState em memória; recarregar a página apaga qualquer cadastro ou registro feito na sessão.
  • Sem autenticação: o login apenas escolhe qual perfil simular — não há verificação de credenciais nem sessão real.
  • Responsável fixo: a jornada do responsável está presa a ALUNO_DEMO_ID ("a1"); não há seleção entre múltiplos dependentes.
  • Plano de ação não retroativo: alunos já em risco nos dados semeados só recebem plano de ação após o próximo indicador ser registrado.
  • Duas fontes divergentes: .html e .jsx são mantidos manualmente em paralelo — uma alteração visual precisa ser replicada nos dois arquivos.
  • Sem testes automatizados no front-end: a estratégia de testes do projeto (unitário/integração/sistema) está descrita em "Plano e Execução de Testes de Software".
